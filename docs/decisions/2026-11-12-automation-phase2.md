# 자동화 Phase 2 결정 기록: 캡처 갱신 절차 고정

- 날짜: 2026-11-12
- 근거 설계: 자동화 파이프라인 설계안의 Phase 2. Phase 1(PR #32)이 검증·패킷 구간을 자동화했고, 남은 최대 수동 병목은 캡처 갱신 오케스트레이션이었다.

## 결정

캡처 갱신 절차를 runbook과 실행 계획 스크립트로 고정한다. 실행 자체는 자동화하지 않는다.

- `evals/capture-runbook.md` 신규: 갱신 조건, 역할(운영자·케이스별 actor 19개·독립 리뷰어), 무결성 경계(기대값을 본 뒤 actor 브리핑 작성 금지), 실패 보존 규칙, 검증 명령을 고정한다. PR #30의 5회 실패와 PR #31의 재사용 성공에서 확립된 절차를 문서화한 것이다.
- `scripts/capture_plan.py` 신규 (표준 라이브러리만): base..head diff에서 변경된 정책 파일을 판정하고, 현재 캡처 참조와 케이스 목록, 예상 산출 경로, 실행 순서를 담은 계획서를 생성한다. 케이스 정보는 id만 싣고, 프롬프트는 scenarios.json에서, 기대값은 계획서에 일절 싣지 않는다.
- `tests/test_capture_plan.py` 신규: 갱신 필요 판정과 계획서 렌더링 테스트 6개.
- `evals/README.md`: runbook 연결 한 문단 추가.

## 기각한 대안

- actor 실행의 완전 자동화: 에이전트 세션 실행을 CI나 데몬에 맡기는 것은 Phase 3 범위다. 절차가 파일럿으로 검증되기 전에 실행까지 자동화하면 실패 원인을 추적하기 어렵다.
- runbook 없이 스크립트만: 계획서만 있으면 절차의 고정 부분(무결성 경계, 실패 보존)이 사람마다 달라진다. PR #30의 실패 원인이 바로 절차 미고정이었다.
- 캡처 재생을 CI가 자동 갱신: 재생은 검증이지 생성이 아니다. 자동 생성된 캡처는 독립 리뷰어의 의미 검수 없이 들어갈 수 있어 게이트 구조와 충돌한다.
