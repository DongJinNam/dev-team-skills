채택 항목은 이 문서를 정본으로 두고 Phase 1부터 별도 PR로 나눠 적용한다. 이 PR 자체는 아무 패턴도 코드나 스킬에 적용하지 않는다.
세 프로젝트 모두 젊고(생성 2026-03, 2026-07, 2026-10) 검증된 수치가 홍보 수치와 어긋나는 사례가 실제로 있었기 때문이다. 패턴은 가져오되 의존성은 만들지 않는 것이 전제다.
채택 단계는 기존 채택 계약의 표기를 따른다. 셋 다 현재 INSPECTED까지만 확정이다. APPLIED와 VERIFIED는 각 Phase PR이 통과한 뒤에만 쓴다.

## 채택 후보와 실행 순서

- Phase 1 (저위험, 기존 CI로 검증 가능): 카탈로그 생성과 규칙 코드화(A1), dry-run materialize diff(C2), observe에서 auto로 올리는 승격 절차 문서(B3), Mandate 헤더를 PR 템플릿과 검수 패킷에 추가(B1).
- Phase 2 (구조 변경): authored config와 generated lock으로 매니페스트 생성 전환(C1), 리뷰 bot 경로에 결정적 gate를 코드로 강제(B2), 워커 격리와 재개 재검증을 engineering-squad 계약에 반영(B4·B5), 백엔드·보안 focused path(A3).
- Phase 3 (파일럿, 별도 검수): Adyen CLI를 보조 설치 경로로만 시험, 역할 번들(Collections), 하네스 트레이스 도해.

항목별 세부 근거와 대조표는 이 결정을 뒷받침하는 분석 기록에 있으며, Phase별 PR에서 해당 항목을 다시 인용한다.

| 대안 | 장점 | 기각 또는 보류 이유 |

| Adyen CLI를 릴리스 경로로 즉시 도입 | 동기화 문제를 한 번에 해결한다 | Antigravity(공식 검증 1순위 플랫폼)와 Windows(패키지 계약 포함)가 빠져 있다. schema 변동 속도도 빠르다. 도구가 아니라 설계만 가져오는 쪽이 차단 사유를 전부 피한다 |

가장 강한 반론은 "셋 다 검증이 끝나지 않은 젊은 프로젝트라 기록할 가치도 없다"는 것이다. 절반은 맞다. 그래서 이 문서는 채택이 아니라 INSPECTED 단계의 결정 기록이며, 가져오는 것도 의존성이 아니라 각 repo에서 확인된 구조(카탈로그 파생, 불변 인가, config와 lock 분리)로 한정했다. 젊다는 사실 자체가 보류 사유로 항목마다 적혀 있다.

## 검증 계획과 한계

- 이 PR은 문서 1개만 추가한다. 코드, 스킬 본문, 매니페스트, CI를 바꾸지 않으므로 기존 하네스 검증과 테스트가 그대로 통과해야 한다.
- 반영 항목의 효과는 아직 실측이 없다. Phase 1 항목이 머지되고 CI와 evals로 확인되기 전에는 토큰 절감이나 속도 개선 같은 효과를 주장하지 않는다.
- 인용한 stars와 레슨 수는 시점 값이다. 다시 인용할 때 날짜를 붙인다.
- dsh의 설계 에세이 수치(p95 단축, 토큰 배수)는 합성 워크로드 기반 주장이라 이 문서에서도 근거로 쓰지 않았다.
