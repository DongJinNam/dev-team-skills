# 현재 모델의 4조건 예비 비교 결과

이번 3개 과제에서는 dev-team-skills가 Superpowers·ECC와 같은 검토 통과 수를 보였고 실행 시간과 캐시 포함 처리 토큰은 더 적었다.
같은 `gpt-6-astra / high`로 12회 실행한 뒤 고정 자동검사와 조건명을 가린 독립 검토를 적용했으며, 발견한 Codex 스킬 로드 오류는 실험 후 별도로 수정했다.
다만 조건당 3회뿐이고 기본 설정보다 시간·토큰이 늘었으며 비캐시 입력량은 Superpowers·ECC보다 많아 일반적 우수성·비열등성·금전 비용 절감까지 입증하지는 못한다.

## 결론과 수치

Windows, Codex CLI 0.167.0, ChatGPT 로그인, 모델 `gpt-6-astra`, 추론 `high`를 모든 실행의 실제 세션 기록에서 확인했다. 세 과제는 JSONL 집계 버그 수정, 페이지네이션 구현, 실제 CLI에 맞는 문서 수정이다. 조건별로 각 과제를 1회씩 수행했다. 모든 실행은 300초 안에 종료됐으며 추가 사용자 힌트·모델 재시도·모델 대체는 없었다.

| 조건 | 고정 자동검사 통과 과제 | 독립 검토 포함 통과 | 3과제 총시간 | 실행 처리 토큰 | 그중 비캐시 입력 토큰 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Codex 기본 | 3/3 | 2/3 | 192.788초 | 199,005 | 21,588 |
| Superpowers 7.0.1 | 3/3 | 3/3 | 244.544초 | 396,843 | 51,137 |
| ECC 2.2.3 | 3/3 | 3/3 | 264.462초 | 423,439 | 52,541 |
| dev-team-skills 실험 snapshot | 3/3 | 3/3 | 226.567초 | 334,900 | 61,619 |

시간은 각 시도의 로컬 파일 준비·로그인 확인·모델 실행 합계이며, 평가 도구 제작·독립 검토·채점 시간은 제외했다. 실행 처리 토큰은 CLI `turn.completed.usage`의 입력+출력으로, 캐시 입력을 포함한다. reasoning 출력은 output의 부분집합이므로 다시 더하지 않았다. 자식 모델 호출은 0회다. 외부 평가자·실험 준비의 토큰을 포함한 전체 작업 비용은 UNMEASURED이며 금액을 계산하지 않았다.

이 표본에서 dev-team-skills는 Superpowers 대비 **시간 7.35%, 처리 토큰 15.61% 감소**, ECC 대비 **시간 14.33%, 처리 토큰 20.91% 감소**였다. 기본 설정 대비는 **시간 17.52%, 처리 토큰 68.29% 증가**했다. 캐시 적중량이 달라 비캐시 입력은 반대로 dev-team-skills가 두 스킬보다 많다. 따라서 ‘토큰이 적으니 더 저렴하다’고 해석하면 안 된다.

## 기본 설정의 2/3은 무엇을 뜻하나

사전에 고정한 자동검사는 버그 수정 32개·기능 추가 21개·문서 5개였고, 네 조건 모두 58/58을 통과했다. 자동 점수만 보면 차이가 없다.

조건명을 모르는 별도 검토자 `/root/artifact_review`가 기본 조건의 버그 수정 산출물에서 두 종류의 공개 계약 위반을 발견했다. `splitlines()`가 JSON 문자열 내부의 U+2028/U+0085까지 행 경계로 잘라 유효 입력을 거부했고, 기본 `json.loads()`가 추가 필드의 `NaN`/`Infinity`/`-Infinity`를 허용해 잘못된 JSON을 받았다. 나머지 세 조건의 구현은 LF 기준 분리와 `parse_constant` 거부 처리를 갖췄다.

검토 후 모든 조건에 동일한 **사후 탐색 검사 5개**를 적용했다. 기본은 0/5, Superpowers·ECC·dev-team-skills는 각각 5/5였다. 이 검사는 원래 58개에 몰래 추가하지 않았고, 고정 점수와 독립 검토 판정을 별도 열로 보존했다. 후보 코드를 고치거나 같은 모델을 다시 실행하지 않았다. 처음 채점기에 이 경계값이 없었다는 한계도 함께 기록한다.

독립 검토는 후보 파일만 익명 ID로 제공해 수행했다. 12개 모두 위험한 파일·네트워크·명령 부작용과 편집 범위 문제는 없었다. 문서 과제의 `toy_cli.py`는 Windows에서 생성한 원본 CRLF 바이트와 모두 일치했다. 검토자는 코드를 실행하지 않았으며, 정적 실행 안전성을 확인한 후 임시 인증 사본이 모두 제거된 상태에서 숨은 검사를 실행했다. 채점 subprocess에는 인증 환경 변수를 전달하지 않았다. subprocess 자체를 보안 sandbox라고 주장하지 않는다.

## 실제 실행 범위와 재현 증거

- 승인: 사용자가 4조건×3과제, 회당 최대 5분, 별도 API 결제 없이 현재 계정 사용량으로 실행하는 안에 “오케이”라고 답했다.
- 조건: 기본 시스템 지침/동일 도구 + 해당 조건의 native `.agents/skills`. 현재 대화·사용자 AGENTS·다른 플러그인 설정을 실험에 복사하지 않았다. ECC/Superpowers/dev-team의 전체 제품 설치가 아니라 **스킬 지침 계층** 비교다. 후보별 AGENTS, MCP, hooks, 자식 모델은 포함하지 않았다.
- 기본 조건에는 추가 패키지가 없으며, 세 패키지는 동일한 위치에 스킬을 복사하고 명시적으로 해당 진입 스킬을 읽게 했다. 실제 읽기 명령은 audit에 보존했다. ECC 문서 과제는 `verification-loop`, 코딩 과제는 `tdd-workflow`; Superpowers는 `using-superpowers`; dev-team은 `engineering-squad`로 시작했다.
- 순서: 버그는 기본→Superpowers→ECC→dev-team, 기능은 Superpowers→ECC→dev-team→기본, 문서는 ECC→dev-team→기본→Superpowers. 각 시도는 새 git root와 CODEX_HOME, 동일 권한·시간 제한을 썼다.
- 버전: Superpowers 설치본 7.0.1; ECC 2.2.3 commit `d2ef2680594f9a17526a6e1a2e18b3d242c5d17b`; dev-team은 base `633e36d`의 스킬 snapshot `a51008d3d15b87a5dc0d22ac5c2738625c38cc3a2a47ae2c3e556fe700aa667b`다. **BOM 수정 전** 스킬로 실행했으며 도중 정책 변경은 0건이다.
- [전체 결과·사용량·모델·검토 해시](../../evals/runs/2026-11-07-four-arm/results.json), 같은 디렉터리의 과제별 코드/테스트/최종 답변/audit/stderr와 [사후 검사 코드](../../evals/runs/2026-11-07-four-arm/posthoc_probe.py)를 보존했다. 사용자 경로를 마스킹하고 인증 파일·비공개 reasoning 세션 기록은 포함하지 않았다.
- [기본 대비](../../evals/runs/2026-11-07-four-arm/vs-basic.json), [Superpowers 대비](../../evals/runs/2026-11-07-four-arm/vs-superpowers.json), [ECC 대비](../../evals/runs/2026-11-07-four-arm/vs-ecc.json)는 기존 집계기로 생성했다. 전 과정 토큰은 미계측이므로 이 파일의 `total_tokens` 평균은 null이고, 위 표의 actor 토큰과 구분한다.

위 짝 비교 입력의 `installed=true`와 출력의 `installation 3/3`은 이 실험에서 정책 파일 준비와 진입 스킬 사용 가능을 뜻한다. marketplace 설치 성공이나 전체 스킬의 정상 로드를 뜻하지 않으며, 기본 조건은 추가 설치가 없는 준비 완료 상태다. dev-team의 humanizer 로드 실패도 이 값에 포함되지 않으므로 전체 패키지 적용률로 인용하지 않는다. 실제 설치·발견 결과는 별도 증거 파일을 따른다.

최종 검토에서 audit에 제삼자 스킬 전문이 포함된 것을 발견해 정책 경로를 읽는 명령의 출력을 생략했다. 명령·종료 코드·상태와 경로 마스킹 후 출력의 UTF-8 바이트 수·SHA-256은 보존했다. 같은 명령에 섞인 과제 출력도 함께 생략했으므로 공개 audit는 원본 전체가 아니다. 과제 산출물·점수·사용량·실험 소스 해시는 변경하지 않았다.

또한 일부 PowerShell `Get-Content` 호출이 인코딩을 지정하지 않아 정책 출력에 깨진 비ASCII 문자가 관찰됐다. dev-team은 진입 스킬을 UTF-8로 다시 읽었지만 모든 조건의 전체 정책이 동일하게 해석됐다고 보장할 수 없다. 이는 실제 Windows 사용상의 관찰이면서 비교의 통제 한계다. 이번 수치를 순수한 스킬 효과로 해석하지 않으며, 후속 실험은 모든 조건의 읽기 인코딩을 먼저 검증해야 한다. 승인된 12회 외에 재실행하지 않았다.

## Codex 적용 결함의 추가 수정

세 dev-team 실행에서 `humanizer/SKILL.md: missing YAML frontmatter delimited by ---`가 발생했다. 주 스킬 engineering-squad는 읽혔으므로 업무 결과는 평가할 수 있었지만, 전체 패키지 로드는 불완전했다.

`humanizer/SKILL.md`와 `SKILL_en.md`에 UTF-8 BOM이 있었다. 기존 하네스는 `utf-8-sig`로 BOM을 지운 뒤 검사했고, BOM 입력을 통과시켜야 한다는 테스트까지 있었다. 두 파일의 시작 3바이트만 제거하고 스킬 검사에서 BOM을 거부하도록 수정했으며 영어 variant도 검사한다. LF/CRLF·공백/한글 경로 지원은 유지하고 JSON 매니페스트의 인코딩 처리는 바꾸지 않았다.

회귀시험 2개가 먼저 실패한 뒤 수정 후 통과했다. 실제 Codex `app-server`의 `initialize`→`skills/list`로 모델 호출 없이 수정 전후를 확인했다. 고유 스킬 발견 수는 **7/8→8/8**, 로드 오류는 **1→0**이었다. 기존 호환용 engineering-squad 별칭이 중복되어 전체 엔트리 수는 8→9이며, 이를 서로 다른 9개 스킬로 세지 않았다. [실제 조회 결과](../../evals/runs/2026-11-07-codex-discovery.json).

## 해석과 다음 실험

이 표본은 dev-team-skills가 사용 가치가 있다는 구체적 근거다. 기본 조건에서 나온 결함이 dev-team 결과에는 없었고, 두 추가 스킬과 같은 검토 통과 수를 더 짧은 시간·적은 처리 토큰으로 얻었다. 그러나 단순 과제 3개·각 1회이므로 이를 모델의 안정적인 성공 확률, 모든 프로젝트에서의 우수성, 또는 통계적 비열등성으로 일반화할 수 없다. 캐시·시점·과제 순서·외부 평가자의 영향도 남아 있다.

실무 도입은 **소규모 과제에서 조건부 채택**으로 판단한다. 다음 실험에서는 이번 사후 경계값을 미리 고정한 테스트에 포함하고, 실제 저장소 작업·큰 변경·복수 반복·동일 캐시 조건 및 전 과정 사용량을 확보해야 한다. 원하는 개선폭·허용 열등 폭과 표본 수는 실행 전에 정하며, 12회 결과가 좋다는 이유로 추가 모델 실행을 자동 승인하지 않는다.
