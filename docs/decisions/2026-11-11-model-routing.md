# 모델 라우팅 계약 도입 결정 기록

> 기준: dev-team-skills main `8f890bf` (2026-11-11 확인). 요청: 사용자 (2026-11-11) — 추론·분석은 고급 모델로, 단순 코드·테스트 작성은 가성비 모델로 나누는 방식을 Claude·Codex·Antigravity·Cursor 각 호스트에 맞게 스킬에 반영하는 것이 우선이다.

## 무엇을

작업 종류별 모델 등급(DEEP/STANDARD/LIGHT) 배정 계약을 engineering-squad에 추가한다. DEEP는 설계·분석·판정·보안 검수와 분석 요약, STANDARD는 확정된 구현·테스트 작성, LIGHT는 판단이 얇은 대량 작업이다. 보안 판정은 DEEP 고정이며 비용을 이유로 내리지 않는다.

## 어떻게

- 신규 참조: `skills/engineering-squad/references/model-routing.md`와 영문판 `model-routing_en.md`. 호스트별 모델표와 고정 수단·강제 수준을 확인일(2026-11-11)과 함께 적는다
- `.agents/skills` 미러를 같은 내용으로 갱신한다 (MIR-001)
- SKILL.md/SKILL_en.md 비용 절 첫머리에 라우팅 계약 연결 한 문단을 추가한다
- SKILL.md가 eval 캡처 snapshot 대상이라 캡처를 갱신한다. 케이스별 독립 세션 actor 19개와 별도 의미 검수로 만들고, 워크플로와 evals README의 현재 캡처 참조를 새 파일로 교체한다 (PR #30에서 확립한 절차)

## 왜

지금까지 비용 절은 사용량 비교 방법만 정했고, 어떤 작업을 어떤 모델로 보낼지는 정하지 않았다. 사용자 운용 방식(Claude는 Opus를 추론·분석에, Sonnet을 구현·테스트에)은 이미 정해져 있으나 스킬에 없어 호스트가 바뀌면 재현되지 않는다. 호스트 4종의 공식 문서를 확인한 결과 고정 수단의 유무와 강도가 제각각이었다. Claude Code는 SKILL·서브에이전트 frontmatter로 강제할 수 있고, Codex는 에이전트 TOML이 있어야 하며, Cursor는 서브에이전트 파일로 모델 ID를 고정할 수 있고, Antigravity는 등급만 지정할 수 있다. 그래서 계약의 본체를 모델명이 아니라 등급으로 두고, 호스트별 표에서만 모델명과 강제 수준을 다루는 구조로 했다.

## 대안과 기각 이유

- SKILL.md frontmatter에 model을 직접 지정: engineering-squad 전체가 한 모델로 고정돼 등급 배정과 충돌하고, 호스트마다 필드 유무가 달라 기각했다.
- 모델명만 나열한 표로 대체: 모델 은퇴·개명이 잦아(Codex는 2026년에만 은퇴 2건) 금방 낡고, 강제 수준의 차이가 사라져 기각했다.
- 기존 비용 절에 문장만 추가: 호스트별 고정 수단과 미확인 경계가 길어 참조 문서로 분리하는 기존 구조와 맞지 않아 기각했다.

## 한계와 재판단 조건

- 이 계약은 라우팅의 효과 실측이 아니다. 토큰·비용 변화는 compare_usage 실측이 있을 때만 주장한다.
- Antigravity 개인 계정에서 pro 등급 지정의 실효성은 미확인 보고 수준이다. 실제 모델 확인 기록이 쌓이면 표를 갱신한다.
- 호스트가 모델 라인업을 바꾸면 표의 확인일을 갱신한다. 등급 정의 자체를 바꿀 때만 이 결정을 개정한다.
