# AI 에이전트 독립 보안 검수자 운영안 (제안)

## 판정 요약

보안 검수 계약의 독립 검토자를 AI 에이전트로 운영할 수 있도록, 패킷 기반 입력 분리, 위험 등급별 게이트, 기계적 강제 결합을 정의한 운영 가이드를 제안한다.
채택되면 `docs/ai-security-reviewer-guide.md`를 정본으로 두고, 실제 도입은 과거 PR 백테스트를 통과한 조직부터 등급별로 넓힌다.
기존 계약이 검토자의 독립성과 증거를 요구하면서도 AI 검토자 특유의 실패 모드(맥락 오염, 검토자 대상 인젝션, 모델 맹점 중복, 판정의 비강제성)는 다루지 않았기 때문이다.

## 무엇이 확인되었나

점검 기준은 `main`의 보안 검수 계약(`skills/engineering-squad/references/security-review.md`)이다.

| 항목 | 확인 결과 | 조치 |
| :--- | :--- | :--- |
| 검토자 요건 | 구현자와 다른 검토자, 현재 head에 대한 PASS와 보고서가 머지 조건. 별도 검토자가 없으면 BLOCKED | 계약을 바꾸지 않고 AI 검토자가 이 요건을 채우는 운영 방식만 정의한다 |
| AI 리뷰의 지위 | 계약 첫머리: "스캐너 통과나 AI 리뷰는 안전성 보증·인증이 아니다" | 가이드 전 구간에서 판정을 보증으로 표현하지 않고, T3 최종 서명을 사람에게 남긴다 |
| 기계적 강제 | 계약: "기계적 강제는 별도의 보호 규칙·신뢰할 수 있는 필수 상태 검사 설정으로 구성" | 강제 장치를 가이드의 필수 결합 요소로 명시하고, 문서만으로 잠긴다고 주장하지 않는다 |
| 외부 전송 | 계약: 코드·데이터를 외부 분석 서비스로 전송하려면 기존 권한과 데이터 정책을 먼저 확인 | 코드 반입 규칙을 도입 전제 조건으로 분리한다 |
| 검토 대상의 지시 | 계약의 AI·스킬·MCP 검사: 외부 지시를 신뢰하지 않고 프롬프트 인젝션을 확인 | 검토자 본인에게도 같은 원칙을 적용한다. 코드와 PR 설명 안의 지시는 데이터로만 취급한다 |

## 토론과 대안

대안은 세 가지였다.

| 대안 | 장점 | 기각 또는 보류 이유 |
| :--- | :--- | :--- |
| 현행 유지 (사람 검토자만) | 조직적 독립성과 책임 소재가 명확하다 | 검토자 부재 시 전 PR이 BLOCKED로 남는 병목이 그대로다. 계약이 허용한 "별도 검토자"의 형태를 좁힐 근거도 없다 |
| AI 검토자를 전 등급 단독 게이트로 | 가장 빠르고 병목이 사라진다 | AI 리뷰는 보증이 아니라는 계약과 충돌한다. 인증·결제·개인정보 변경까지 단독으로 두면 맹점 중복과 책임 공백이 남는다 |
| 등급별 차등 (채택 제안) | T1은 속도를 얻고 T3은 사람의 최종 책임을 유지한다 | 운영 규칙과 백테스트라는 추가 비용이 든다. 이 비용을 가이드에 명시했다 |

가장 강한 반론은 "검토자도 결국 같은 사용자의 에이전트라 조직적 독립성이 없다"는 것이다. 맞는 지적이라서 가이드가 판정 해제를 사람 명의의 잔여 위험 수용 기록으로만 허용하고, 검토자가 압박으로 판정을 바꾸지 않는 규칙을 분리 원칙에 넣었다. 구조적 독립성을 흉내 내지 않고 한계로 남긴다.

## 검증 계획과 한계

- 이 PR 자체는 문서만 변경한다. 코드, 스킬 본문, 매니페스트, CI를 바꾸지 않으므로 기존 하네스 검증이 그대로 통과해야 한다.
- 가이드의 효과(재현율, 오탐, 소요 시간)는 아직 실측이 없다. 도입 검증 절의 백테스트를 통과하기 전에는 어떤 조직에서도 게이트 적용을 주장하지 않는다.
- 백테스트 표본과 통과 기준은 도입하는 조직이 자기 워크로드로 정한다. 이 문서는 방법만 제공한다.

## 이 PR의 보안 검수

문서 전용 변경이다. 작성자는 이 PR의 독립 검토자가 아니므로 판정은 PENDING으로 둔다. 머지 전에 계약대로 작성자와 다른 검토자가 최신 head에 대해 범위를 줄인 검수(문서 내 링크·지시 문구의 인젝션 여부, 내부 정보 포함 여부)를 하고 PASS를 발행해야 한다.
