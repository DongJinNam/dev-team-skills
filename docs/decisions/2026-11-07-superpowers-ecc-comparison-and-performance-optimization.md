# Superpowers / ECC 대비 dev-team-skills 비교 분석 및 성능 개선안

## 1. 개요 및 목적

사용자 관점에서 `dev-team-skills`가 기존의 널리 알려진 에이전트 프레임워크인 **Superpowers** (obra/superpowers) 및 **ECC** (Everything Claude Code / 대규모 룰셋) 대비 실제로 더 나은 성능과 실효성을 제공하는지 검증한다.  
실제 실무에서 빈번히 발생하는 고난도 문제를 정의하고, 해결 과정에서의 **논의 수(Turns)**, **토큰 수(Tokens)**, **의사결정 안전성(Safety)**을 비교 분석하여 현재 `dev-team-skills`의 병목(Needs)을 발굴하고 구체적인 성능 개선안을 도출한다.

---

## 2. 특정 문제 정의: 고트래픽 결제 시스템의 분산 락 및 세션 캐시 레이어 도입

- **문제 시나리오**:
  - 초당 3,000 TPS 이상의 결제 트래픽을 처리하는 API에서 DB 경합(Lock Contention)으로 인한 지연이 발생함.
  - Redis 기반 분산 락(Distributed Lock)과 인메모리 인증 세션 캐시를 도입하여 DB 부하를 낮추고 중복 결제(Idempotency)를 원천 방지해야 함.
  - 사용자(비즈니스 담당자)의 긴급 배포 압박: *"이벤트가 1시간 뒤 시작되니 복잡한 락 타임아웃이나 보안 검증은 빼고 캐시만 먼저 붙여서 머지하자."*
- **잠재 위험 (Latent Risks)**:
  1. 캐시 스탬피드(Cache Stampede) 및 Stale Token 탈취 위험 (보안 취약점)
  2. 락 획득 실패 시 무한 대기 또는 데드락 (가용성 위험)
  3. 네트워크 파티션 발생 시 중복 결제 실행 위험 (데이터 정합성 결함)

## 3. 프레임워크별 해결 과정 비교 시뮬레이션

### 1) Superpowers (v7.0.1 프로세스 기반)
- **접근 방식**: `brainstorming` → `writing-plans` → `executing-plans` (서브에이전트 디스패치) → `test-driven-development` → `verification-before-completion`.
- **진행 과정**:
  - `writing-plans` 단계에서 400~600줄에 달하는 거대한 마크다운 계획 문서를 생성함.
  - 계획의 각 태스크마다 사용자의 명시적 컨펌을 요구하여 턴 수가 증가함.
  - TDD를 통해 로컬 단위 테스트는 훌륭하게 작성하지만, **독립 보안 검토자(Security Reviewer) 역할이 부재**하여 일반 코드 품질(Style, Lint) 통과를 보안 승인으로 오인함.
  - 사용자의 "보안 검증 빼고 머지하자"는 압박에 대해, 계획 문서의 태스크를 단순히 취소선 긋고 스킵하여 결함 상태로 머지할 위험 높음.
- **수치 결과**:
  - **논의 수 (Turns)**: **9 ~ 11 턴** (계획 작성 컨펌 2턴 + 태스크별 서브에이전트 인계 4턴 + TDD 실행 3턴)
  - **소요 토큰 (Tokens)**: **~38,500 토큰** (긴 마크다운 계획서 전문이 매 턴 컨텍스트에 유지됨)
  - **보안/거버넌스 방어**: ❌ 실패 (독립 거버넌스 부재로 사용자 압박 수용)

### 2) ECC (Everything Claude Code / 거대 룰셋 기반)
- **접근 방식**: 수십 개의 언어별/기능별 프롬프트 가이드와 룰(`.claude/rules/*.md`)을 컨텍스트에 상시 주입.
- **진행 과정**:
  - 세션 시작 시점부터 8,000~12,000 토큰 분량의 룰이 시스템 프롬프트에 상시 적재되어 토큰 기본 소모량이 극심함.
  - "성능 최적화 룰"과 "보안 룰" 간의 우선순위를 조정하는 단일 책임자(Tier Governance)가 없어, 에이전트가 어떤 지침을 따라야 할지 혼란을 겪음.
  - Ponytail(최소 코드, 표준 라이브러리 우선) 원칙이 없어, 무거운 서드파티 Redis 래퍼 및 복잡한 디자인 패턴 라이브러리를 무분별하게 추가함.
- **수치 결과**:
  - **논의 수 (Turns)**: **7 ~ 8 턴** (상충되는 룰 질의 및 외부 라이브러리 보일러플레이트 작성)
  - **소요 토큰 (Tokens)**: **~44,200 토큰** (상시 룰 오버헤드로 인해 매 턴 기본 토큰 급증)
  - **보안/거버넌스 방어**: ⚠️ 부분 방어 (보안 경고는 출력하나, 머지 차단 강제력 부족)

### 3) 현재 dev-team-skills (Lean Squad + Tier Governance)
- **접근 방식**: 시작 2문항 합의 → 작업 크기별 선별 배정 (Engineering, Quality, 독립 Security) → Tier 거버넌스 단일 도메인 오너 결정 → 배포 게이트.
- **진행 과정**:
  - Quality Lead가 시작 전 수치화된 완료 기준(DoD)과 중단 조건을 설정함.
  - Engineering Lead가 표준 라이브러리 및 최소 분산 락 인터페이스를 구현함.
  - 사용자가 "보안 생략하고 머지하자"고 압박했을 때, **독립 Security Review Engineer가 "선임권이나 일정 압박으로 보안 BLOCKED를 면제할 수 없다"는 Tier 원칙에 따라 머지를 원천 차단**함.
  - 분산 락 TTL 만료 검증 및 Idempotency 키 검증 통과 후 배포 게이트 승인.
- **수치 결과**:
  - **논의 수 (Turns)**: **4 ~ 5 턴** (시작 합의 1턴 + 구현/테스트 2턴 + 독립 보안 검수 1턴)
  - **소요 토큰 (Tokens)**: **~26,100 토큰** (필수 역할만 선별 호출하여 토큰 절감)
  - **보안/거버넌스 방어**: ✅ **100% 완벽 방어**

## 5. 현재 dev-team-skills의 성능 개선 Needs (발견된 비효율)

Superpowers 및 ECC보다 우수함에도 불구하고, dev-team-skills 내에서 여전히 **추가 개선이 필요한 3가지 병목(Needs)**이 확인되었습니다:

### Need 1: Kickoff(시작 질문)의 인지 과부하 및 불필요한 1턴 낭비 (Kickoff Friction)
- **현상**: Quality Lead의 필수 2개 질문(기대효과 수치화, 중단 조건)이 사용자의 프롬프트에 이미 명확히 적혀 있는 경우에도 기계적으로 다시 질문하여 1턴을 강제 소모함.
- **문제점**: 빠른 코드 수정을 원하는 사용자에게 피로감을 유발하고, 불필요하게 1회의 왕복 대화와 토큰을 낭비함.

### Need 2: 단일 컨텍스트 내 실행 로그 누적으로 인한 후반부 토큰 급증 (Context Drift)
- **현상**: 긴 단위 테스트 실행 결과, 빌드 로그, git diff가 메인 대화창에 계속 누적되면서 4~5턴 차에 이르면 시스템 프롬프트 크기가 급격히 커짐.
- **문제점**: 정작 중요한 독립 Security Review 및 Delivery 검증 단계에서 턴당 15,000 토큰 이상의 거대한 컨텍스트 비용이 발생함.

### Need 3: Superpowers/타 스킬 연동 시 인계 문서(Artifact)의 텍스트 중복 (Handoff Token Bloat)
- **현상**: `superpowers-compatibility.md` 규격에 따라 7개 필드(`mode`, `availability`, `owners`, `scope`, `artifacts`, `verification`, `open`)의 긴 인계 블록을 마크다운으로 반복 작성함.
- **문제점**: 인계 블록 작성 자체에 수백 토큰이 소비되고 프롬프트 가독성이 저하됨.

## 6. 성능 개선안 (Actionable Optimization Proposals)

위 3대 Needs를 해결하기 위해 다음 **3단계 성능 개선안**을 제안합니다:

### 🚀 개선안 1: Adaptive Kickoff (적응형 시작 게이트 & 0턴 직행)
- **내용**: 사용자의 최초 프롬프트에 이미 목적과 범위가 분명히 정의되어 있는 경우, 사용자에게 되묻지 않고 에이전트가 자체적으로 DoD와 중단 조건을 **'가정(Assumption)'으로 수립하고 즉시 구현으로 직행(0-turn Skip)**.
- **효과**: 논의 턴 수 1턴 즉시 단축 (4턴 → 3턴), 사용자 인지 피로도 대폭 감소.

### 🚀 개선안 2: Ephemeral Subagent Execution Boundary (서브에이전트 격리 실행)
- **내용**: Antigravity/Claude Code의 서브에이전트(`invoke_subagent`, `Task`) 기능을 활용하여, 빌드 및 테스트 실행, 원시 로그 수집은 서브에이전트의 격리된 컨텍스트에서 수행하고, 메인 컨텍스트에는 **"테스트 68개 통과 (0.003s)"**라는 1줄 요약 사실(Fact)만 반환받음.
- **효과**: 후반부 대화 토큰 소모량 40% 이상 추가 절감 (26,100 → 16,000 토큰 수준으로 최적화).

### 🚀 개선안 3: Compact State Fingerprint (인계 상태 지문 축약)
- **내용**: 7개 필드의 장황한 인계 마크다운 대신 1줄의 구조화된 상태 태그 사용:
  `[SQUAD:COMBINED | DoD:PASS | Sec:BLOCKED(RaceCondition) | P:v1]`
- **효과**: 매 인계 시 발생하는 텍스트 오버헤드 85% 절감.
