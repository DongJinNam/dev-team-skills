# 외부 저장소 기여: 증거와 인계 양식

외부 저장소의 코드를 수정해 PR을 준비할 때만 읽는다. 기존 역할·권한·검증 계약을 아래 양식으로 연결하며 새 역할이나 상시 회의를 만들지 않는다. 도구를 가져다 쓰는 작업은 [활용 계약](./tool-adoption.md)을 사용한다.

## 1. 기여 대상과 범위

Lead가 필요한 Product/Engineering/Quality 역량을 배정하고 다음 기록을 유지한다.

| 기록 | 확인할 내용 |
| --- | --- |
| 사용자 적합성 | 사용자의 분야·원하는 기여 종류·제외 범위. 코어 개선 요청이면 재현 가능한 버그·경계 조건·회귀 테스트를 먼저 검토한다. 번역으로 범위를 바꾸려면 사용자 결정을 받는다. |
| 저장소 상태 | upstream URL·기준 브랜치/SHA·확인일, 최근 릴리스/유지보수, 관련 이슈·중복 PR. stars는 발견 단서이며 수용 가능성의 증거가 아니다. |
| 기여 조건 | LICENSE와 CONTRIBUTING·PR 템플릿·기여 검사에서 CLA/DCO·추가 계정·인증·비용·사전 이슈 합의 요구를 각각 확인한다. 미확인은 UNKNOWN으로 남긴다. |
| 선택 근거 | 재현 입력→기대/실제 동작, 사용자 영향, 수정 범위, 검증 비용, 호환성, 필요한 maintainer 합의. 요구된 조건과 맞지 않으면 다른 후보를 제안한다. |

허용적 라이선스만으로 “조건 없는 기여”를 보장하지 않는다. GitHub 로그인과 프로젝트가 추가로 요구하는 서명/인증을 구분한다. 명시된 사전 합의 요구가 없고 기존 계약을 복구하는 국소 버그 수정이면 사용자가 허용한 로컬 작업을 진행할 수 있다. 새 API·의도된 동작 변경·큰 설계에는 upstream의 합의 절차를 확인한다. 어느 경로도 maintainer의 수용이나 머지를 보장하지 않는다.

## 2. 검증 기록

Quality가 기존 도구로 하나의 `AC | revision | 명령/환경 | 실행 범위 | 기대/실제 | 결과 | 로그/한계` 표를 유지한다.

- 버그 회귀는 변경 전 코드에서 의도한 실패, 변경 후 성공을 기록한다. 새 테스트를 이전 코드에 적용한 방법도 남긴다. 미실행을 실패 재현으로 쓰지 않는다.
- 지연 조회·캐시·풀 상태 변경은 실제 드라이버 반환값(정규화/null), 반복 변경·무효화, 실패 후 재시도, 읽지 않고 반납할 때 복원, 기본 설정 부재 중 관련 경계를 확인한다. 매번 전부 실행하는 고정 목록은 아니다.
- 먼저 저장소의 기본 테스트 선택과 CI 명령을 확인한다. 기본·집중·추가 스트레스·외부 서비스 테스트의 실행/건너뜀/제외를 구분한다. 발견한 실패는 유지하며 같은 조건의 변경 전 코드로 대조해 신규/기존/환경/미확인으로 분류한다. 기존 실패라는 이유만으로 필수 게이트를 면제하지 않는다.
- Docker 등 실행 환경이 없으면 원래 테스트는 NOT_RUN으로 유지한다. 로컬 실제 DB 같은 대체 검증은 실행한 메서드·드라이버/DB 버전·어댑터·원래 실행과의 차이를 별도 기록한다. 대체 결과를 원래 전체 suite PASS로 쓰지 않는다.
- 성능은 같은 입력·반복 수·환경·warmup 조건의 변경 전/후를 비교한다. 쿼리 수·지연·처리량은 다른 지표다. 측정하지 않은 시간·운영 성능·토큰 절감은 UNMEASURED다.

## 3. 게시 전 인계

Lead가 최종 편집 후 아래 필드를 채운다. 기존 승인과 중단 계약을 재사용하고 영향을 받은 변경만 다시 확인한다.

```text
대상: upstream/fork, base 브랜치와 SHA, head 브랜치와 SHA
범위: 사용자 목적, 관련 이슈, 파일 목록/개수, 커밋 수, 추가/삭제 줄 수
제목/본문: 실제 게시할 최종 문자열
검증: 실행 명령·결과·건너뜀/제외·실패·대체 검증 한계, 측정 지표
권한: 로컬 수정/게시/머지의 허용 범위, 최종 승인 조건과 근거
남은 조건: 미검증·차단 사유, 필요한 다음 행동
```

통계는 의도한 신규 파일까지 포함한 완성된 변경에서 계산한다. `git status --short`와 staged/unstaged diff로 포함 대상을 확인하고 관련 파일만 stage한다. 최종 커밋 뒤에는 대상 base와 head의 merge-base 기준 diff/stat 및 커밋 목록을 사용한다. `git diff --stat`만으로 untracked 파일을 누락하거나 `git add .`로 무관한 파일을 포함하지 않는다. 민감한 로그는 공개 본문에서 제거한다.

사용자가 최종 승인을 요청했다면 이 패킷을 먼저 제시하고 승인 전 PR을 생성하지 않는다. 이미 승인한 동일한 내용·대상·범위라면 같은 승인을 다시 묻지 않는다. 변경 내용/대상/본문이 승인 범위를 벗어나면 변경분을 보여주고 해당 게시를 대기한다. PR 생성 권한은 머지·배포 권한이 아니다.

## 4. 게시와 확인

1. 실제 쓰기 기능과 권한을 확인한다. 읽기 성공은 쓰기 가능의 증거가 아니다. connector/CLI/브라우저는 호스트가 허용하고 해당 계정·저장소·데이터에 대해 승인된 경로만 사용한다. integration 403을 숨기거나 반복하지 말고 실패와 가능한 경로를 기록한다. 정책 차단·승인 거절을 우회하거나 토큰/권한을 임의로 확대하지 않는다.
2. 업로드 뒤 remote head의 전체 diff/파일 내용을 검증된 로컬 변경과 대조한다. 같은 base의 Git tree 비교를 사용할 수 있다. 커밋 메타데이터 때문에 SHA가 달라져도 내용 일치는 별도 검증할 수 있지만 기존 head-bound 보안 PASS를 새 SHA로 복사하지 않는다. 미일치/미확인은 해당 PR 생성을 대기하고 원인을 확인한다.
3. 생성 뒤 PR URL·Open/Draft 상태·base/head·제목/본문·파일 통계를 읽어 확인한다. CI는 관찰한 상태로만 보고한다. 생성·검사 통과·리뷰 승인·머지는 각각 다른 결과다. 머지는 기존 독립 보안·컴플라이언스·QA 계약과 별도 권한을 따른다.

영문 PR은 문제와 바뀐 동작부터 짧게 쓰고 검증·한계를 이어 쓴다. 자연스러운 문체로 다듬되 인간이 수행하지 않은 검토·테스트를 했다고 쓰거나, upstream이 요구한 AI 기여 공개를 누락하지 않는다.
