# Tier별 의사결정 계약

## 1. 권한과 역할

이 계약은 기존 자동 다수결 선택 규칙을 대체한다. 먼저 안건의 범위·가역성·영향 분야·결정 책임자·위임 근거를 기록한다. 사용자가 정한 목표·예산·권한과 상위 지침이 우선한다. Tier는 역할의 책임 범위이며 모델 등급이나 추가 호출 의무가 아니다.

| Tier | 기존 역할 / 책임 | 보고·충돌 해결 경로 |
| --- | --- | --- |
| 1 | **Tech Lead (Squad Lead / Main Agent의 동일 역할)**: 전체 구조·공통 계약·분야 간 우선순위·위험 조정 | 미위임 전략·예산·권한 변경은 사용자 |
| 2 | **Product Planner / Product Lead**: 승인된 목표 안의 제품 우선순위·PRD·메시지 정합성 | Tech Lead |
| 2 | **AI Agent Engineer / Engineering Lead**: 하네스와 승인된 구조 내 구현 방향·기술 검증 조정 | Tech Lead |
| 2 | **Test Engineer / Quality Lead**: 완료 기준·검증 계획·누락 테스트 판단 | Tech Lead; 필수 미검증은 통과시킬 수 없음 |
| 2 | **DevOps Engineer / Delivery Lead**: 배포 계획·운영 인계·복구 준비 | Tech Lead; 배포 권한은 별도 |
| 2 | **Finance / FinOps**: 비용 근거·한도 안의 절감안 | Tech Lead; 한도 변경은 사용자 |
| 2 | **Security Review Engineer**: 독립 보안 판정 | Tech Lead에 직접 차단 보고; 판정은 security-review.md 적용 |
| 2 | **Compliance Reviewer**: 적용 법규·라이선스 검토와 차단 | Tech Lead에 직접 보고; 불명확한 해석은 전문 검토 |
| 3 | **Frontend Engineer, Backend Engineer, Data Engineer**: 승인된 계약 안의 구현·계층 테스트 | Engineering Lead |
| 3 | **QA Engineer**: 기능·회귀 테스트 실행과 증거 | Quality Lead |
| 3 | **SRE Engineer**: 신뢰성·관측·복구 검증 | Delivery Lead; SLO/구조 충돌은 Tech Lead |
| 3 | **Product Marketing, Creative Rookie**: 메시지·사용자 근거, 반론·작은 실험 | Product Lead; 안전/권한 문제는 Tech Lead에 직접 보고 |

14개 역할과 Lead를 재배치한다. Humanizer Editor와 Ponytail은 편집·단순화 책임이며 별도 결정권을 추가하지 않는다. 작은 작업에서는 Lead가 분야 책임을 겸임하고 겸임 사실을 기록한다. 비활성 분야의 동의를 만들어내거나 모든 역할을 호출하지 않는다. 독립 보안 검수는 구현자/Lead의 겸임으로 대체하지 않는다. Tier 2의 기술 책임은 해당 분야 전문가의 증거를 모아 판단하는 책임이며 모든 분야의 전문성을 보유한다는 뜻이 아니다.

## 2. 결정 경로

| 관찰 조건 | 결정 책임자와 처리 |
| --- | --- |
| 승인된 계약 안의 국소·가역 구현 | Tier 3가 구현 재량을 행사하고 증거를 보고; 대안 선택이 필요하면 해당 Tier 2가 결정 |
| 한 분야 안의 대안, 목표·예산·공통 계약 유지 | 해당 Tier 2가 근거·반론을 검토해 결정; 무관한 역할의 표를 기다리지 않음 |
| 공통 API/데이터 계약 변경, 다분야 충돌, 구조·일정·비용 간 우선순위 충돌 | Tier 2가 대안·영향·권고를 올리고 **Tech Lead**가 위임 범위 내에서 조정·결정 |
| 미위임 목표·수용 기준·예산 한도·외부 게시/배포 권한 변경, 되돌리기 어려운 외부 영향 | **사용자**에게 선택지·영향을 보고하고 필요한 승인까지 해당 실행은 PENDING |
| 필수 QA·독립 보안·적용 컴플라이언스 실패/증거 부재 또는 합의된 중단 조건 발생 | 해당 실행 BLOCKED; 해결·재검수 또는 기존 권한자의 명시적 재개 필요 |

수평 자문은 가능하나 다른 분야 파일·계약을 강제로 바꾸지 않는다. 분야 내 충돌은 해당 Tier 2, Tier 2 간 충돌은 Tech Lead로 올린다. 책임자가 없으면 Tech Lead가 지정한다. Tech Lead가 부재하고 지정 대리인도 없으면 상위 결정은 PENDING으로 남긴다. 자기 결정의 중대한 이해충돌이나 전문성 부족은 공개하고 적절한 검토자/사용자에게 올린다.

## 3. 근거 → 반론 → 책임 결정

1. 제안자는 동일 버전의 질문·범위·2–3개 대안(단순한 경우 현 상태와 제안)·검증 증거·비용/위험·되돌릴 방법을 작성한다. 사실·가설·미확인을 구분한다.
2. 관련 역할에 자문하고 반론 1회를 검토한다. Creative Rookie의 반례도 같은 기준으로 검토하며, 반대 의견을 이유 없이 묵살하지 않는다. 불참자의 동의를 추정하지 않는다. 추가 토론은 새 근거·기대 가치를 기록한다.
3. 책임자는 정확성·사용자 가치·단순성·유지보수·검증 가능성·비용·가역성으로 선택을 설명한다. 다수 의견과 다르면 왜 반론을 수용하지 않았는지와 재판단 조건을 명시한다. 근거 부족은 **PENDING**, 필수 차단은 **BLOCKED**로 남긴다. 상위 직급도 사실을 증명하거나 차단을 면제하지 못한다.
4. **15표·8표는 요청 시 자문용 집계**다. 8표 도달은 실행·자동 가결·머지 승인이 아니다. 7표와 미제출 8개도 충분한 근거와 권한을 가진 분야 책임자의 결정을 막지 않는다. 수집한 표만 기록하며 투표수로 안전성·사실을 입증하지 않는다.
5. **사용자 재검토/재투표 요구**는 팀 허가 없이 즉시 접수한다. 안건 버전·사용자 근거를 기록하고 미실행 후속 행동을 보류한다. 이전 결정·반론은 이력에 보존하며 새 자문에는 과거 표를 이월하지 않는다. 해당 책임자가 재검토하고, Tech Lead 결정에 대한 이의는 사용자가 최종 판단한다. 사용자가 직접 결과를 지정하면 그 범위를 따르되 필수 게이트와 도구 권한은 유지한다.

## 4. 판정과 실행 권한을 분리

`DECIDED`는 책임자의 대안 선택 완료, `PENDING`은 근거/필요 승인 부족, `BLOCKED`는 필수 게이트·중단 조건으로 실행 불가다. `DECIDED`여도 실행 준비 상태는 BLOCKED일 수 있다. 최신 head/base 독립 보안 PASS, 기능 QA, 적용 컴플라이언스 위반 해소 및 기존 배포 게이트를 별도로 확인한다. 이 계약은 GitHub 보호 규칙이나 호스트 권한을 자동 설정하지 않는다.

사용자가 자율 판단을 명시적으로 맡기면 **작업·기간·결정 범위·예산/권한 한계·종료 조건**을 기록한다. “이번 과정 한정” 위임은 그 작업 종료/취소로 만료하며 다음 프로젝트에 이어지지 않는다. 침묵은 승인/재개가 아니다. 범위 안의 일상 결정을 매번 다시 묻지 않되, 사용자 요구와 필수 보안/컴플라이언스·중단 계약은 유지한다. 기존 kickoff 질문은 이 계약만으로 생략할 수 없다. 일반적인 결정 위임만으로 직접 시작 질문·합의 또는 중단 후 재개를 대신하지 않는다. 별도의 명시적 사용자 지시가 기존 절차를 이번 작업에 한해 변경했다면 그 원문·변경 범위·만료를 기록하며 Lead 판단을 사용자 답변으로 꾸미지 않는다. 미래 프로젝트에는 기존 질문 규칙을 적용한다.

## 5. 필수 결정 기록

```text
안건 ID/버전·범위·영향 분야·가역성:
결정 책임자/tier·실제 담당자/겸임·위임 근거/유효 범위:
대안·확인된 증거·가설/미확인·비용/위험·롤백:
자문 참여자·반론·수용/미수용 이유·미참여/공백:
선택/근거·판정(DECIDED/PENDING/BLOCKED):
실행 준비(READY/PENDING/BLOCKED)·QA/보안/컴플라이언스·필요 승인:
실행 담당·검증 기준·재판단/중단 조건:
사용자 이의·이전 결정·위임 만료:
```

작은 결정은 기존 작업 기록에 필요한 필드만 짧게 남긴다. 별도 조직 회의·전체 에이전트 재호출은 필요하지 않다.
